# 人工复核功能（本地实现）

已实现真实待复核队列、接受/拒绝、修改已保存决定、调整问题归组、人工补充、问题确认与跟进、合并与拆分，
原文变化后的重新复核，以及操作历史、版本校验、幂等提交、账号登录与角色权限。
评论、问题组和人工复核分别通过 `/ui/#/comments`、`/ui/#/issues`、`/ui/#/reviews` 使用原产品 API，
不使用独立期中 Demo 的数据库。`/ui/#/batches` 已接通真实 CSV 上传与批次进度。
当前账号适用于团队共享工作区，不做店铺/商品级隔离。

## 交付验收

本地实现与开发验收已经完成；推送、创建 PR 和合并是独立操作，按用户明确确认执行。
已核对远端分支名称为 `human-review`（不是早期讨论中写的 `hunman-review`）。
交付前查询时，远端 `human-review` 和 `main` 均在 `1ddc68b`；实际推送前应再次检查远端是否前进。

在独立验收环境中，使用自己的样例商品/来源编号依次检查：

| 步骤 | 操作 | 应看到的结果 |
| --- | --- | --- |
| 1 | 复核员登录，上传两条有效评论和一条缺少店铺的 CSV | 新增 2、无效 1；显示无效记录位置，后台完成两条有效评论的分析 |
| 2 | 批次详情进入评论，选中有问题的评论进入建议复核 | 原文和引文一致；接受后返回能看到新决定及账号名 |
| 3 | 修改决定、填写原因后刷新 | 新旧决定均保留在历史中，页面读取最新状态 |
| 4 | 对当前有效的已接受证据确认问题，再跟进、解决、重开 | 状态转换正确，各次说明和操作者可追溯 |
| 5 | 人工补充证据，并检查调整归组、合并/拆分 | 证据来自原文；归组前后的历史保留，确认状态按规则重置 |
| 6 | 同一来源编号上传修改后的正文 | 保留旧正文；旧人工证据标作待重核，核对后可以保存新决定 |
| 7 | 退出并用只读账号登录 | 可以查看批次、评论与历史，不能上传或提交复核 |

## 运行

使用 Python 3.11，安装 `pip install -e '.[dev]'`，配置 `.env` 后运行：

```bash
docker compose up --build -d
```

Compose 中 API 启动时执行 `alembic upgrade head`，当前迁移末版为 `20261121_0006`。
直接使用 uvicorn 启动时，先手动执行 `alembic upgrade head`。
打开 http://localhost:8000/ui/#/reviews 。实际端口遵从 `API_HOST_PORT`。
通过批次上传页或 `POST /review-batches` 导入评论，由已有 Worker 和规则 AI 产生建议。
待复核为空表示没有符合当前条件的建议，不会用模拟记录填充。

本次验收环境另使用本机端口 18080（API）、18101（AI）、18201（Worker 指标）、55437（PostgreSQL），
数据库 `human_review_test`，Docker 容器 `pri-human-review-test`。这套数据仅供本地验收。

## 评论、问题组与复核的页面联调

三个页面共用登录会话和角色权限。未登录时展示登录入口；只读成员可查看原文、关联、问题组和历史，
复核员可通过既有复核接口提交。所有真实数据均来自 API；空结果显示空状态，网络失败显示重试提示，
不会回退为 mock。批次上传页也使用同一套会话和真实数据。

- 评论列表支持批次编号、商品编号、分析状态、AI 判断和正文关键词筛选，每页 20 条；总数来自后端。
  缺失评分、评论日期显示“未提供”；不显示模拟置信度。分析尚未完成时，已有 AI 判断标作上次结果。
- 评论详情展示当前原文、全部关联的真实问题标题、接受/拒绝状态、来源和决定者。
  旧证据、归档关联与原文/分析变化有独立提示；可以进入指定关联复核，或为这条评论人工补充。
- 问题组列表支持商品、状态（含单独的已合并）、类别、标题搜索和分页。
  未归档已接受关联数与当前有效证据数分别展示；历史或暂不可用的已接受关联不作为当前确认依据。
- 问题组详情复用 `IssueWorkflow` 的确认、跟进、处理、驳回、重开及合并/拆分逻辑，
  原文、证据分页、关联历史和问题级历史保持同一契约。可跳转评论详情、指定复核记录及合并/拆分另一侧。
- 在复核页保存后，点击返回评论/问题组详情会重新请求 API；列表也有显式刷新入口。
  没有实时推送，其他人的修改需重新加载；提交仍由已有 token 和版本规则处理并发冲突。
- 筛选和页码保存在 URL 中，详情页返回列表时保留；浏览器刷新可以恢复定位。
  页面切换后，旧的异步响应不会覆盖新页面；找不到详情时显示说明及重试/返回入口。

路由契约：

| 地址（相对 `/ui/`） | 用途 |
| --- | --- |
| `#/comments?product_id=…&analysis_status=…&has_issue=…&q=…&page=2` | 评论筛选与分页 |
| `#/comments/{id}` | 指定评论详情；可携带列表筛选参数 |
| `#/issues?status=confirmed&category_id=…&product_id=…&q=…&page=2` | 问题组筛选与分页 |
| `#/issues/{id}` | 指定问题组详情；可携带列表筛选参数 |
| `#/reviews?mode=decisions&id={link_id}` | 指定关联的复核与历史 |
| `#/reviews?mode=manual&id={comment_id}` | 指定评论的人工补充 |
| `#/reviews?mode=issues&id={issue_id}` | 工作台内的问题组跟进 |

复核路由可附加 URL 编码的 return_to；只接受评论/问题组内部地址，并保留其筛选条件。
其他协议、外站地址和非法路径不会成为返回链接。工作台内部切换更新当前深链接；
首次进入关联时根据实际状态选择待复核、已处理或待重核列表，不假定所有传入记录都已处理。

数据接入复用现有接口：

- `GET /comments` 仍返回原来的 JSON 数组，新增 q（最多 200 字）和 `X-Total-Count` 响应头。
  关键词按字面匹配，百分号/下划线不会扩展成 SQL 通配符；按 created_at 倒序、id 正序稳定分页。
- 评论详情复用 `GET /review-comments/{id}`，一次返回当前评论和带问题信息的关联快照。
- 问题列表/详情/证据分别复用 `GET /review-issues`、`GET /review-issues/{id}`、
  `GET /review-issues/{id}/evidence`；写入仍使用原有动作接口，不增加另一套状态转换。
- 本阶段不新增数据库迁移，末版仍为 `20261121_0006`。

## 真实批次上传与分析进度

入口 `/ui/#/batches`：复核员填写平台标识并选择 CSV；只读成员可查看记录和进度，不能上传。
使用现有 JSON 接口传输 `csv_text`，没有增加文件存储服务或 multipart 依赖。

- 文件为 UTF-8（可带 BOM）、不超过 10 MiB，最多 5,000 条数据记录，正文最多 2,000 字符。
  页面提供可下载示例，示例行必须换成实际数据。正文中的逗号或换行应包在双引号中。
- 必填列 `shop_id,product_id,body`；可选列 `source_review_id,review_date,rating`。
  店铺/商品编号最多 64 字符，来源编号最多 128 字符；评分为 0–5 整数，日期为 ISO 日期/时间。
  没有来源编号时仍沿用后端合成去重编号的规则。
- 字段错误、多余单元格、超长编号和 NUL 字符按行报告，有效行仍可导入。
  缺少必填列、重复/空/非法表头、空文件、引号结构错误、超行数或文件大小上限会整批拒收。
  未知列只产生提示，不计入无效行。CSV 表头为第 1 条记录，多行引号字段仍是一条记录。
- 同一浏览器会话内，相同文件名、平台和文件内容复用请求 UUID，刷新页面后也能重试。
  sessionStorage 仅保存摘要与 UUID，不保存评论正文；存储不可用时退回当前页面内存。
  后端保存请求摘要并在 PostgreSQL 中串行处理同一幂等键，避免并发重试重复建批次；
  同键不同内容返回 409。旧批次没有摘要时保留原重放规则。
- 批次列表按平台/文件名筛选，每页 20 条；详情可刷新、收藏，返回保留筛选和页码。
  列表显示持久化的**导入阶段**，详情另外显示由后台任务与当前评论计算的**处理进度**。
- 详情分别展示导入时读取/新增/重复来源/无效行，以及当前关联评论的完成/等待/失败数。
  重复来源包含正文未变的去重和正文改变的更新，并不表示所有重复行都被忽略。
  覆盖率以当前关联评论为分母，没有当前评论时为“不适用”；后续重导后评论可能归入新批次。
  更新可能继续使用旧批次的活动任务，因此同时检查当前评论的等待状态，避免过早显示完成。
  历史任务失败也会保留在任务计数中。整批拒收时“无效行”不代表每行都已检查。
- 等待分析时每 5 秒刷新，完成后停止；离开页面停止后续请求。断网显示错误和手动重试，
  不将旧数据当作刚刷新的结果。导入后可跳到 `#/comments?batch_id=…`，再查看 AI 建议并人工复核。

接口增补（本阶段没有新迁移）：

- `GET /review-batches`：`platform,q,limit,offset`，返回 `BatchRead[]` 和 `X-Total-Count`。
- `GET /review-batches/{id}`：保留原字段，增加 `batch` 导入元数据、`current_rows,waiting_rows,failed_jobs`；
  `analysis_coverage` 修正为当前关联评论的分析覆盖率，避免更新旧评论时超过 100% 或错误为空。
- `GET /review-batches/{id}/errors` 沿用原错误列表；上传返回的 422 中含 batch_id 时，前端进入拒收详情。
- `GET /comments` 增加精确 `batch_id` 筛选，与原筛选及总数头组合使用。
- `batch-pages.js` 负责真实批次页，`batch-upload.js` 处理文件读取与重试键；主页面已移除 mock 数据脚本引用。

## 登录、角色与账号管理

`.env.example` 明确使用 `REVIEW_AUTH_MODE=demo`，保留课程演示兼容性。
此模式不验证账号，页面仍标明“演示身份（非登录认证）”，默认操作者为 `demo-reviewer`。
账号模式使用 `REVIEW_AUTH_MODE=session`，未登录时业务接口返回 401，复核页面显示登录表单。
配置不合法或数据库不可用时，不会自动退回演示身份。

| 角色 | 查看范围 | 写入权限 |
| --- | --- | --- |
| viewer（只读成员） | 共享工作区的评论、批次、问题、证据、历史和统计 | 无；人工补充、复核、归组、重核、问题跟进、合并/拆分及批次导入均返回 403 |
| reviewer（复核员） | 与只读成员相同 | 可执行上述业务写入，仍受原文、状态、版本和证据校验约束 |

没有公开注册接口或网页管理员入口。维护者在项目运行环境内创建账号，密码由终端隐藏输入，
不通过命令行参数、前端或数据库明文保存。账号规范化为小写，3–64 位，以字母开头；
其余字符为字母、数字、下划线、点或连字符。账号名不可重命名、删除后复用；
现有演示身份及已用于审计记录的名称不能注册为新账号。

本地源码运行示例（先配置 DATABASE_URL 并执行迁移）：

```bash
python -m services.api.app.auth.manage create alice --role reviewer
python -m services.api.app.auth.manage create bob --role viewer
python -m services.api.app.auth.manage password alice
python -m services.api.app.auth.manage role alice --role viewer
python -m services.api.app.auth.manage disable alice
python -m services.api.app.auth.manage enable alice
```

Compose 环境可使用 `docker compose exec api python -m services.api.app.auth.manage create alice --role reviewer`。
密码为 12–256 个字符，不允许全为空格。改密、改角色、停用或重新启用账号，都会撤销该账号全部旧会话。
历史 operator/decided_by 仍保存原账号名，不随停用或角色改变而修改。

启用本机 HTTP 预览时配置：

```dotenv
APP_ENV=development
REVIEW_AUTH_MODE=session
REVIEW_COOKIE_SECURE=false
REVIEW_SESSION_HOURS=8
```

修改配置后重启 API；Compose 使用 `docker compose up -d --force-recreate api`。
正式部署使用 HTTPS、`REVIEW_COOKIE_SECURE=true`，并把 `APP_ENV` 设置为部署环境名称。
除 development/test 外的环境必须同时使用 session 模式和 Secure Cookie，否则配置校验拒绝启动。
反向代理须保留正确 Host/协议，并仅信任自己的代理转发头；页面与 API 使用同一源。
本模块不提供组织 SSO、邮箱重置密码、多因素认证或租户级权限；共享工作区内的两个角色按上表授权。

会话及接口约定：

- `GET /auth/session`：返回 mode、authenticated、username、role、can_review、csrf_token、expires_at。
  未登录时也返回 200，但 authenticated=false、can_review=false；不返回密码或原始会话令牌。
- `POST /auth/login`：JSON 仅包含 username、password。请求须带 `X-Review-Request: 1`。
  浏览器的 Origin 必须与 API 同源；跨站请求被拒绝。错误密码/未知/停用账号统一返回 401。
- `POST /auth/logout`：撤销当前会话并删除 Cookie；其他设备的独立会话不受影响。
  已登录时须携带 CSRF 头；已过期时仍允许同源清理 Cookie。
- 会话令牌通过 HttpOnly、SameSite=Strict Cookie 保存，数据库仅存 SHA-256 摘要；不放在 localStorage。
  绝对有效期默认 8 小时，可配置 1–24 小时，不因页面访问自动延期；登录会轮换当前浏览器的旧令牌。
- 账号模式的所有业务写入须同时携带 Cookie、`X-Review-Request: 1` 和当前会话的 `X-CSRF-Token`。
  页面登录后自动处理；脚本客户端也应先登录、保存 Cookie，再使用响应中的 csrf_token。
- 后端从当前有效会话读取账号角色，复核审计由后端填入 operator，忽略不了也绕不过权限检查。
  详情中的 can_decide/can_add/allowed_actions 等表示业务条件，客户端还须结合会话 can_review；
  只读页面隐藏或禁用写入入口，直接请求写入仍会被后端拒绝。
- 未登录不能通过原有 `/comments`、`/issues`、批次、任务或统计接口绕过权限读取真实数据。
  健康检查、指标、静态页面和 OpenAPI 文档保持可访问；真实业务数据仍由 API 鉴权。
- 所有 API 响应禁止缓存。会话过期、退出或权限失效时，复核工作台清空当前内容并要求重新登录，
  不自动重试原提交；其他标签页退出也通知当前页面。旧请求的延迟失败不会清除后来登录的新会话。
- 登录限流持久化在数据库：15 分钟内每个账号名最多 5 次失败，每个客户端地址最多 30 次尝试。
  未知账号同样计数，成功登录清零该账号失败次数；超过限额返回 429，可在窗口结束后重试。
  地址来自请求连接信息，共用反向代理地址时会共享地址额度。
- 账号写锁先于业务锁：已授权进行中的写入先完成；停用/改权提交后，排队的写入重新检查会话并拒绝。
  同 UUID 的旧回执仍绑定实际操作者，另一账号不能借旧请求编号复用其决定。

0006 新增 review_users、review_sessions、review_login_throttles，保留所有原有业务表及审计数据。
本次仅在隔离本地库创建了验收账号，账号说明位于仓库外，不作为项目默认账号发布。
过期会话在该账号后续成功登录时清理；大规模部署可另行制定过期会话和限流桶的保留/清理策略。

密码使用独立随机盐的 PBKDF2-HMAC-SHA256（600,000 次），不增加第三方认证依赖；参数参考
[OWASP 密码存储说明](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。
CSRF 采用会话绑定令牌、自定义请求头及同源校验，参考
[OWASP CSRF 防护说明](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

## 结构与契约

- `services/api/app/reviews/router.py`：十七个复核 HTTP 接口，操作者来自认证依赖。
- `services/api/app/auth/`：登录/会话/退出、全局业务权限、密码校验与本地账号管理命令。
- `queries.py`：队列及详情，关联数与去重评论数不混用。
- `rules.py`：当前原文、分析记录、关联和问题版本的有效性。
- `commands.py`：同一事务保存决定、版本、审计快照和请求回执。
- `reassign.py`：目标问题组查询、归组事务与两侧审计。
- `manual.py`：评论筛选、人工证据、新建/已有问题组关联与事务审计。
- `issue_workflow.py`：问题组状态转换、当前证据有效性、跟进记录与问题级审计。
- `structure.py`：合并目标预览、冲突检测、合并/拆分事务与双侧历史。
- `recheck.py`、`history.py`：重新核对当前原文、更新人工证据，并按精确摘要找回可核验的旧原文。
- `services/common/locking.py`：Worker 和归组操作共用的 PostgreSQL 类别锁。
- `frontend/api-client.js`、`review-ui.js`、`reassign-ui.js`：真实页面；保留现有 hash 路由。
- `manual-review-ui.js`、`issue-workflow-ui.js`、`review-shell.js`：人工补充、问题组跟进与三个入口之间的切换。
- `issue-structure-ui.js`：合并目标选择、拆分勾选、影响预览与原因填写。

- `auth-ui.js`：工作台登录入口、会话状态、角色提示与退出。
- `product-pages.js`、`product-routes.js`：真实评论/问题页面、筛选分页、深链接与安全返回地址。
  `app.js` 只保留公共导航、说明页和批次模拟页，不再保留模拟评论/问题组及其假保存操作。

## 修改决定的交互与审计

在“已处理”列表选择记录 → 点击“修改决定” → 填写修改原因 → 改为相反决定。
取消修改只退出表单，不调用写入接口。成功后更新关联状态、决定人/时间和 review_version，
追加 action=change 的 issue_actions；原接受/拒绝记录保持不变。
新记录的 payload_json 保存 operation=revise_decision、previous_action_id、前后状态与操作者，
以及当时原文/证据。第一阶段的回执哈希保持兼容，旧请求重放不撤销后来作出的修改。
本次增补复用 0004 的字段，不需要再添加迁移。

## 原文变化后的重新复核

入口为“建议复核与历史” → 记录筛选“原文变化待重核”。此列表显示尚未归档且已有人工决定或人工归组，
其证据所依据的精确正文摘要已与当前评论不一致的关联。它是按关联计算的待办，同一评论可能有多个关联。
正在分析和已关闭问题中的记录也可查询，页面解释当前不能保存的原因。
纯 AI 未处理建议仍走普通复核或人工补充；已归档关联不因原文变化而恢复。

选择记录后，页面分别显示当前原文、旧证据对应的原文、原决定和历史。
点击“重新核对原文与证据”，明确选择本次接受或拒绝，填写原因后保存：

- **接受**必须重新选取当前原文中的非空精确引文，包含 Unicode 字符位置；重复文字可选择具体出现位置。
  即使结果仍是 accepted，只要原文版本不同，重新判断仍是一次独立操作，原接受记录保留。
- **拒绝**允许不提供引文：清空当前证据文字和位置，evidence_verified=false，保存本次依据的完整正文摘要。
  不强迫用户从“已解决/不成立”的新原文中编造问题证据。若提供引文，仍须精确匹配当前原文。
  保存后退出待重核列表，原引文继续留在旧审计中。
- 拒绝后没有证据时，不能用普通“修改决定”直接接受。页面允许再次进入原文与证据重核，
  提供有效引文后明确改为接受。其他缺失/失效的人工证据也允许此修复入口；
  当前正文、决定和证据都不变的重复操作返回 recheck_unchanged，不增加无意义记录。
- 同一原文且证据有效时，仍用原有“修改决定”，不开放任意覆写有效证据。
  重新复核始终要求非空原因，最长 500 字；客户端不能指定 operator。
- 允许 analyzed/failed，不依赖新 AI 判断成功；received/queued/analyzing 期间不可保存。
  关闭的问题需先在问题组流程中明确重开；已合并或已归档的旧关联不可通过重核恢复归组。

保存时保留关联编号，设为 origin=human，以当前正文的 evidence_body_hash 锚定本次判断，
analysis_run_id 清空（原编号保存在历史），更新 comment_version、review_version、决定人和时间。
不改评论正文、AI 的 has_issue/current_analysis_run_id/analysis_status、CommentRevision 或 Job。
所属问题组回到 proposed 并递增版本：需要重新核对整体问题，不能把旧确认直接用于更新后的证据。
问题组原确认、跟进等历史仍保留；也可以根据新证据明确驳回问题组。

旧原文先从本关联审计快照查找，再从 CommentRevision 查找；必须精确匹配原证据摘要，
不只依靠可能不准确的旧 comment_version。无法恢复时返回 evidence_body=null，界面和新审计明确标为缺失，
不复制当前正文冒充旧正文。无稳定来源编号、被导入流程识别为另一条新评论的记录，仍走人工补充/归组流程。

写入按评论 → 关联 → 问题的锁顺序执行，复用 Worker/导入/归组的父评论锁约定；
先检查 token 和当前可操作性，再提交关联更新、问题状态、两条审计和 UUID 回执。
token 也绑定范围、类别、标题、证据校验标记及决定元数据，读入后变化则返回 409，表单保留输入供重新核对。
关联历史 operation=recheck_evidence 保存完整前后证据快照及 previous_action_id；
问题组历史 operation=evidence_rechecked 记录被重核关联、前后状态和原文，可双向查看。
任一审计写入失败全部回滚，重复 UUID 返回原回执，不撤销后来的改判、正文更新或归组。
本功能复用 0004/0005 和既有 IssueAction，不增加迁移。

## 调整问题归组

选择待复核或已接受的关联 → 点击“调整问题归组” → 搜索/选择目标 → 填写原因 → 确认调整。
目标必须属于同平台、同店铺、同商品，处于 proposed/confirmed 且未被合并；允许跨类别。
原证据必须仍与当前原文精确匹配。已拒绝的原关联不能直接调整；可先按“修改决定”重新判断。

- 原关联保留在原问题下并标记 rejected，递增 review_version。
- 目标不存在该评论关联时创建；已有未人工处理的 AI suggested 关联时复用其 ID，
  包括已被新分析替换的旧建议。复用前的证据写入审计，目标证据沿用原关联的原文片段。
- 目标关联标记 accepted、origin=human，保留源分析编号和评论版本；问题状态不自动改变。
- 目标已接受/已拒绝，或有人工来源、决定人、决定时间时，列表显示禁用项，提交返回 409。
  不覆盖这些决定；原操作可通过“修改决定”单独纠正，本阶段没有整笔归组撤销功能。
- 两边各追加 action=change，operation 分别为 reassign_out/reassign_in，
  共用 operation_id，记录原/目标关联、问题标题、前后快照及 previous_action_id。
  页面可从两边历史互相跳转。原记录和之前的历史不删除。
- 源 token 与目标 token 分别校验，目标 token 包括问题元数据和目标关联的存在性/版本。
  其他人修改目标、创建目标关联或改变源内容后，旧页面不能直接覆盖。
- 源决定、目标决定、两条历史和唯一请求回执在同一事务提交，失败全部回滚。
  相同请求重试返回原回执，不撤销后续修改。

归组锁顺序为评论 → 原关联 → 按类别排序的 advisory locks → 按 ID 排序的两个问题 → 目标关联。
Worker 也先按相同顺序锁类别，再更新建议和问题，避免不同评论跨类别操作时互相等待成环。
SQLite 测试不模拟行锁；相关并发行为由真实 PostgreSQL 测试覆盖。

## 人工补充问题

入口为“人工复核”页顶部的“人工补充问题”。默认查看 AI 未发现问题、无法判断或分析失败的评论，
可切换到全部评论，也可从关联详情直接为同一评论补充其他问题。无任何 AI 建议的评论同样可进入。
当前支持 analyzed/failed；received/queued/analyzing 暂不允许补充，避免在变化中的分析上提交。
列表是评论筛选，不是“尚未处理”队列：补充后 AI 原判断不变，评论仍可在相同筛选下找到。

复制原文证据 → 选择出现位置 → 关联已有问题组或新建 → 填写原因 → 保存。
重复文字可选择第几处，页面高亮所选位置。界面和后端都采用 Unicode 字符位置，包含 emoji 时也能对应；
后端要求 `body[start:end] == evidence_text`，空白证据、错误位置和改写的引文均不接受。

- 已有目标遵循同平台/店铺/商品、有效状态规则，允许复用未经人工处理的旧 AI 建议。
  该评论在目标中已有人工决定时拒绝覆盖，并提供查看原关联的入口。
- 新问题必须填写标题（最多 200 字）和合法类别；保存为 proposed、created_by=human。
  同范围同类别已有有效同名问题时返回 duplicate_issue（忽略大小写、合并空白），要求明确选择已有目标。
  此项不是语义去重；不同标题可能表达同一问题，仍需复核者判断。
- 人工关联保存为 accepted、origin=human，analysis_run_id 为空，不伪造 AI 分析记录。
  不修改评论正文、has_issue、analysis_status，也不改写 Job。
- 新迁移 0005 为 comment_issues 增加可空的 evidence_body_hash，锚定完整原文的精确 SHA-256。
  人工补充凭此判断原文有效性，不依赖 AI 成功。旧关联字段保持空，继续使用已有分析记录验证。
  后续调整归组会复制此摘要，修改决定和再归组均能处理人工补充的关联。
- 同一事务保存新问题（如有）、关联、审计和幂等回执。历史 operation=manual_add，保存
  created_issue、原 AI 判断/分析状态、前后关联、原文证据、前次动作和原因。失败全部回滚。
- 评论 token 绑定正文、范围、分析状态/编号以及已有关联的版本/决定；已有目标另校验 target token。
  先锁评论，再按 Worker 的类别锁规则处理目标。重复请求返回原回执，不重复建组，也不撤销后续改判。
- 保存后可查看关联及历史，继续使用既有“修改决定”和“调整问题归组”。Worker 重跑保留人工证据。

## 问题组确认与跟进

入口为“人工复核”页顶部的“问题确认与跟进”。可以按状态、商品、类别、标题查询，
选择问题组后核对当前证据，填写说明并保存操作。也可从关联详情的“查看问题组与跟进”进入，
或从问题组证据跳回对应关联与复核历史；这些入口均读取真实 API。

| 操作 | 原状态 | 保存后状态 | 规则 |
| --- | --- | --- | --- |
| 确认问题 confirm | proposed（待确认） | confirmed（已确认） | 至少一条当前有效的已接受证据 |
| 记录跟进 follow_up | confirmed | confirmed | 追加进展，不代表处理完成 |
| 标记已处理 resolve | confirmed | resolved（已处理） | 保存处理说明及 resolved_at |
| 驳回问题 dismiss | proposed / confirmed | dismissed（已驳回） | 保存误判或不成立的说明 |
| 重新打开 reopen | resolved / dismissed | proposed | reopen_count 加一，清空当前 resolved_at，重新核对后确认 |

所有操作都要求非空说明，最多 500 字；已合并的问题组不允许操作。
接受评论关联与确认问题组是两个独立决定；本功能不修改评论正文、AI 判断、Job 或已有的关联决定。
处理完成和驳回也不会删除关联、证据或以前的操作记录。跟进目前是进展记录，不包含任务分派、期限和通知。

- 确认依据是当前有效的 accepted 关联：检查原文、范围、分析状态、是否被替换及引文位置；
  人工补充使用 evidence_body_hash，分析失败时也能提供有效证据。仅有 AI 建议不能确认问题组。
  页面分别显示“已接受关联”和“当前有效的已接受证据”，不混用这两个数量。
- 已确认后如果原文变化或接受决定被撤回，问题状态保留，历史仍表示当时的判断；
  当前有效证据归零时页面提示重新核查，可以明确记录跟进、处理或驳回，不自动改写历史结论。
  当人工明确保存“原文与证据重新复核”时，问题组回到待确认，并追加重核历史。
- 每次操作（包括跟进）递增 Issue.version 并更新 updated_at；问题 token 同时绑定组信息及全部关联、
  原文和当前有效性。读入后发生变化时返回 issue_changed（409），前端保留填写内容供重新核对。
- 写入时依次锁定组内全部评论（按 ID 排序）、与 Worker 共用的类别锁、问题组；
  再检查关联集合和 token。锁定期间新增成员时拒绝旧快照，避免漏掉 Worker 刚加入的评论。
- 问题更新、IssueAction 和唯一请求回执在同一事务保存，失败全部回滚；同请求重试返回原结果，
  不撤销后来作出的操作。operator 由后端提供，客户端不可指定。
- 问题级审计的 comment_issue_id 为空，operation=issue_lifecycle，保存前后状态/版本、处理时间、
  重开次数、当时已接受关联的完整原文与证据及其有效性、previous_action_id。
  问题组历史与单条关联历史分别显示，页面可展开“查看当时的确认依据”。

本阶段复用现有 Issue / IssueAction 字段和迁移 0004 的请求回执，不增加数据库迁移，head 仍为 0005。
Worker 沿用原有范围与类别归组规则，关闭的问题不作为活动目标；新评论会加入其他活动组或新建待确认组。
Worker 不自动重开已处理/已驳回的问题；按语义识别“旧问题再次发生”仍需后续归组能力。

## 问题组合并与拆分

入口在“问题确认与跟进”的真实问题详情，支持 proposed/confirmed 且未合并的问题。
操作原因必填，最多 500 字；关闭的问题需按已有流程先重开。
本阶段沿用已有 merged_into_id、split_from_id、superseded_at 和审计字段，不新增迁移。

**合并：** 选择“合并问题组” → 搜索同平台/店铺/商品的活动目标 → 核对转入、去重及恢复归档数量 → 填写原因 → 保存。
允许跨类别，保留目标标题与类别。源组所有未归档关联参与整理（包含接受、拒绝和待复核），
已归档记录只保留为历史。源组存为 dismissed + merged_into_id，页面单独标为“已合并”，
可跳转目标；“已驳回”筛选排除已合并记录，“已合并”可单独筛选。
源组不再接受新的决定或重开，目标组回到 proposed，需重新核对后确认。

**拆分：** 选择“拆分问题组” → 勾选部分未归档关联 → 填写新组标题、类别与原因 → 保存。
选择必须是原组未归档关联的严格子集，至少留一条在原组；单次最多 100 条，可跨页选择。
新组保存 created_by=human、split_from_id，原组与新组均回到 proposed。
新标题沿用人工补充的同范围/类别活动组去重规则；拆分为多个组可分次完成。

- 原关联不删除，不把接受改为拒绝。通过 superseded_at 归档其成员关系，递增 review_version，
  origin 记为 human 以保护归组决定。原接受/拒绝决定人和时间保持不变，旧历史不改写。
- 目标没有同评论关联时创建新关联，沿用原 status、证据位置、原文摘要、分析编号、决定人/时间。
  原 AI 证据使用原 AnalysisRun.input_hash 作为人工归组后的锚点，绝不改用当前正文重新盖章。
  原文已变化或分析未就绪的关联可保留其历史状态进行整理，但仍不能成为有效确认依据。
- 目标已有同评论关联时，只有决定、证据原文/位置/校验标记和原始正文摘要全部一致才去重，
  保留目标关联编号和决定人/时间。任何差异都会拒绝整笔合并，页面提供两侧关联详情供核查。
  不自动选择“接受优先”或覆盖另一人的拒绝决定。
- 一致的目标关联若已归档，可明确恢复，并在预览和历史中单列“恢复归档”数量。
  因而可以把拆出的组再次合回原组，保留原关联编号；有不同决定或证据时仍要求先处理冲突。
- 两侧问题级历史及逐关联历史均追加 merge_out/merge_in 或 split_out/split_in，
  记录共同 operation_id、两组名称、前后快照、来源/目标关联编号及转入和去重数量。
  原审计属于原组，保持原样；可沿“另一侧问题组”或关联历史入口连续追溯。
- 按 ID 顺序锁定两个组全部相关评论，再按类别锁、问题 ID 锁的既定顺序写入。
  核对双方 token 和成员集合；锁定期间 Worker 新增成员或人工改判时，旧请求返回 409。
  拆分新组与人工补充共用同名检查及类别锁。全部关联、问题、审计和请求回执原子提交。
- Worker 重跑保留原组的归档成员和目标组的人工归组，包括仍为 suggested 的关联；
  这些待复核关联按保留的正文摘要进入真实待复核队列，不因分析编号更新而消失。
  新评论仍使用原有类别基线，尚不能依据此次人工拆分自动学习语义分组。

合并/拆分不改变评论正文、AI 判断或 Job。取消只关闭表单，不发写入请求；
网络失败重试复用 UUID，成功后的重复提交返回原回执，不重复建组或恢复旧状态。
当前没有整笔“撤销合并”按钮；后续整理需新建可审计的拆分或合并操作。

## 一致性规则

1. 先锁评论，再锁关联及问题；与导入/Worker 的评论锁互斥，不操作 Job 锁。
2. Worker 更新或替换建议时递增 `review_version`。人工决定同样递增。
3. token 绑定正文精确哈希、分析记录、关联版本/证据/状态和问题版本/状态。
   它是并发凭据，不是身份认证凭据。读取快照可能随时间变化，最终写入必须重新检查。
4. 首次复核只能处理当前成功分析的有效 AI 建议。修改决定只能针对已接受/已拒绝关联；
   正在分析、失效、原文变化或关闭问题均返回 409。Worker 在相同原文上完成重跑后，
   允许纠正其保留的人工决定，不要求关联的原分析编号变成最新分析编号。
   独立人工补充按 evidence_body_hash 验证，分析失败时也可改判；分析进行中仍阻止提交。
   原文已变化需走专用 recheck 流程，不通过旧 decisions 请求覆盖证据。
5. 接受前再次检查证据位置和文字。拒绝不表示删除评论，也不修改 AI 的 has_issue。
6. 普通接受/拒绝及修改决定保留 origin=ai，通过 decided_by/decided_at 标识人工判断。
   调整归组后的目标关联使用 origin=human，原关联来源保持不变。
7. 决定与 issue_actions 快照一起提交；失败全部回滚。接受关联不自动确认问题组。
8. request_id 有数据库唯一约束。同编号同内容返回原回执，即使原文后来变化；
   同编号不同内容/对象返回 409，不重复写入历史。网络失败后前端重试复用原编号。
9. 审计快照含当时完整正文、证据、问题标题/类别、分析编号及前后状态。
10. 新评论保存初始 revision；旧评论尚无 revision 时，在修改前保存已知原文。
    不重新编号已有历史，不伪造无法恢复的早期正文。历史有效性以精确原文哈希校验，
    不依赖旧数据中可能重合的 comment_version。

## 当前边界

- 默认开发配置仍是明确标注的 demo 模式；账号权限需按上文启用 session 模式。
  当前是团队共享工作区，未实现按用户划分店铺、商品的数据权限。
- CSV 上传、批次进度、评论、问题组和人工复核页均已联通真实 API；模型抽取、语义归组仍属于后续分析工作。
- 已处理记录可显示“原文已变化”，通过待重核筛选及专用表单重新判断，旧审计快照保留。
- 调整归组只选择已有问题组；新建问题组通过人工补充入口完成。
  原文变化或缺失/失效证据通过重新复核更新，不支持任意覆盖当前有效证据，
  也不支持用人工补充操作覆盖历史人工决定。
- 当前队列为保持 SQLite/PostgreSQL 一致，在应用层检查候选正文哈希后分页；
  大数据规模需将精确快照摘要持久化并建立索引。本阶段针对课程批次演示。
- 问题组列表和证据列表使用数据库分页；每组的有效数量与 token 仍会检查该组全部关联，
  单组证据很大时需优化摘要与增量校验。
- 现有问题/汇总统计继续沿用原有累计关联口径；不要把它标作“当前正文已完成复核”。
- 前端复核显示不使用 mock 置信度，也不把相似度当概率。
- LLM 分支可继续沿用此模块；合并时保留 schemas/API 中的 source、fallback_reason 增补。
