# 0. 结论摘要

1. **设计理念成立**：把现有"异步 AI 分析流水线"从 Pitch 反馈迁移到评论治理，原则是"AI 提供线索、人做判断、原文可追溯、失败可见"。单平台、单入口、只做文字评论、只在同一商品内归组——边界收得很干净，是这份 Proposal 最大的优点。
2. **仓库目前不是这个系统的实现**：README 与 `docs/architecture.md` 描述的是 Pitch 反馈助手，`models.py` 是 `Case/Job` 的工单 triage 骨架，AI 服务是关键词匹配；Proposal 需要的 5 张表（Review / IngestionBatch / Issue / ReviewIssue / ReviewRecord）、`has_issue` 三态、原文证据定位、人工复核闭环、去重幂等，代码里一处都没有。可复用的只有工程骨架：四服务 Compose、Job 四态枚举、事务性建任务、JSON 日志、健康检查 / 指标 / CI。
3. **P0 级设计问题 10 个**，其中 6 个是 Proposal 自身不闭合（写下去会出现两种互斥实现），必须在开工前定稿：
   - Job 粒度与"部分成功"未定义；
   - Job 重试目标两图不一致（图 1 `failed→claimed`、图 2 `failed→pending`），`attempts` 位置、上限、触发者都缺；
   - 图 1 把 `confirmed` 之后画成"结束·维持关闭"，`resolved` 与"记录跟进"在端到端图中缺失；
   - `dismissed` 标"终态"与 §4.1"可重新打开已关闭的问题组"矛盾；
   - 评论实体没有 `analysis_status`，导致"接收量 / 成功分析量 / 失败量"无法计算；
   - 重跑（正文变更 / prompt / 模型升级）没有版本与"只写 suggested"规则，会覆盖人工结论。
4. 另外 4 个 P0 是工程必然踩坑：`Review`（评论）/「复核」/`ReviewRecord` 三义命名冲突、AI 契约与证据定位不可校验、错误清单"不落库"、统计口径未定义。
5. **建议先定 8 个决策再开工**（见 §6），开工前冻结契约（OpenAPI + Pydantic schemas）；**协作采用"契约先行 + 四线并行"**（§5.1）：只有契约、迁移执行、联调回归三段串行，其余工作四条工作流并行，每人对自己的测试负责。
6. **交付顺序**：契约与迁移 → 主流程 → 最小闭环联调 → 归组质量与统计口径 → 加固与文档 → 演示与报告。

# 1. 三个文件在讲什么：系统设计解读

## 1.1 一句话定位

商家把**一个平台**上的商品评论（CSV 导入或授权接口拉取）批量交给系统，系统逐条用 AI 提取"具体问题"（类别 + 描述 + 原文证据），把**同一商品内语义相近的问题**归成候选问题组（Issue），运营人员复核、改名、合并、拆分、驳回，并记录跟进结果。系统只做"整理与线索"，不做缺陷判定、不做平台内操作。

目标用户：选定平台上有一定评论量的电商商家、商品运营、售后负责人；演示聚焦**箱包类**商品（拉链、肩带、容量、色差），便于人工核对。

## 1.2 端到端流程（图 1 解读，8 步 + 2 个回流环）

| 步骤 | 系统动作 | 关键设计点 |
| --- | --- | --- |
| 1 选择平台 | 确定唯一接入平台 | 首版是配置项，不是用户可切换的运行态 |
| 2 取得评论数据 | 商家导出 CSV / 授权接口拉取 | 二选一，先验证真实入口；不自行开发采集工具 |
| 3 校验与规范化 | 必需字段、编码、行数上限 | 统一成"平台 / 店铺 / 商品 / 日期 / 正文 / 来源标识" |
| 4 校验通过？ | 否 → 错误清单（行号 + 原因，不落库），修正后重传 | 首版只做同步校验；"不落库"是缺陷（见 P0-10） |
| 5 事务落库 + 建 Job | 评论落库，Job `pending`，接口返回任务号 | 落库与建任务同一事务，提交即返回（202） |
| 6 Worker 认领 + AI 提取 | `claimed`，记录 `claimed_at`、`attempts+1`；输出 `has_issue` 三态、类别、证据 | 一条评论可有多个问题；证据要能在原文定位 |
| 7 输出有效？ | 否 → Job `failed`，记录错误、不伪造；虚线"重试 attempts+1" | 重试是 Proposal 最不闭合的部分（P0-3） |
| 8 同商品归组 + 人工复核 | 更新关联 `suggested`，关联已有 Issue 或新建候选 Issue（`proposed`）；人工确认 / 驳回 / 先调整（改名、合并、拆分） | 归组限定同一商品；人工结论优先；AI 建议数与人工确认数分开展示 |

两个回流环：**错误清单 → 修正后重传**（数据入口质量）、**输出无效 → 重试**（分析可靠性）。两者在首版都只做到"可见 + 人工兜底"，不做自动修复。

## 1.3 三条状态机（图 2 解读）

| 对象 | 状态 | 图 2 画出的迁移 | 设计意图 |
| --- | --- | --- | --- |
| 分析任务 Job | pending / claimed / completed / failed | pending→claimed（认领）；claimed→completed（输出有效）；claimed→failed（失败）；failed→pending（虚线，重试） | 任务完成 ≠ 业务问题解决 |
| 问题组 Issue | proposed / confirmed / resolved / dismissed | proposed→confirmed（确认）；proposed→dismissed（驳回，图注"终态"）；confirmed→resolved（记录跟进）；resolved→confirmed（重开） | 只有人工确认才算成立；处理完成只表示"已记录跟进" |
| 评论关联 ReviewIssue | suggested / accepted / rejected | suggested→accepted（接受）；suggested→rejected（拒绝）；accepted↔rejected（改判） | AI 建议与人工决定分离，允许改判留痕 |

图 2 两条图注决定了数据模型字段：①「改名 / 合并 / 拆分属于属性与关联变更，不改变 Issue 状态；`suggested` 不计入人工确认数，页面分开显示『AI 建议数』与『人工确认数』」；②「Job 若因 Worker 中断停在 `claimed`，首版不自动恢复，需人工核查」。但这两条与图 1、正文、风险表都有冲突（见 §3）。

## 1.4 实体与统计口径

Proposal 拟定 5 个新增实体：**Review**（评论原文与来源）、**IngestionBatch**（接收批次与结果）、**Issue**（问题组与状态）、**ReviewIssue**（评论—问题关联）、**ReviewRecord**（人工修改与跟进记录）；Job 调整关联。

- **去重**：优先「平台 + 店铺 + 来源评论编号」；无稳定编号时验证替代标识，不能因正文相同就删除；重试靠更新或唯一约束避免重复归组、重复计数。
- **更新**：同一来源评论正文变化时保留可追溯更新记录并重新分析，更新受影响的关联与统计；不承诺发现全部历史变更。
- **计数口径**（§5）：问题数量 = 提及该问题的**去重评论条数**，同一评论对同一问题只计一次；页面分别显示接收量、成功分析量、失败量；占比分母是"同一商品、同一时间范围内成功分析的有效评论数"，**不得称为缺陷率或退货率**。
- **归类规则**（§4.3）：先按商品编号限定范围；大类（质量、物流、描述不符、使用体验）→ 具体问题；相似度阈值靠人工标注样本调整，不把相似度当概率；第一版只做简单计数排序。

## 1.5 设计理念（值得保留的 6 条）

1. **复用而不重写**：请求即返回、后台任务、事务落库、失败可见、AI 可插拔——新项目只加"批量接收、集中管理、语义归类、问题组跟进"。
2. **事实与推断分离**：评论原文、来源、时间是不可变事实；AI 的问题提取和归组是推断，必须挂证据、可被人推翻。
3. **AI 提线索、人做判断**：不自动认定缺陷、责任、根因；不自动退款 / 召回 / 下架；不向原平台写操作。
4. **可追溯**：AI 建议与人工结论分开存（`suggested` vs `accepted`），改名 / 合并 / 拆分 / 改判都留记录。
5. **单平台、单入口、单商品域收敛**：不跨平台、不跨商品匹配、不处理图片视频、不做多店铺权限，为后续扩展留字段而不留代码。
6. **统计诚实**：区分"接收量 / 成功分析量 / 失败量"，只报告"评论中的问题提及情况"，不做异常预测。

> 注意：§1 复用清单写"可插拔 AI 服务与**人工复核**"，但 `docs/architecture.md` 明确写着 "A formal approval system and stored review records are outside the initial scope"、"The initial version does not automatically retry failed Jobs"、"automatic recovery is outside the initial scope"。**人工复核、重试、恢复在现有骨架里都不存在，是本项目的新增工作量**，工作量评估时不能按"复用"算。

# 3. 设计问题与修改建议（P0 必须定稿 / P1 首版内做 / P2 有余力再做）

> 问题来源：我对 Proposal + 两张图 + 代码的逐项核对，与两份独立评审（`review/repo-audit.md` 代码审计、`review/design-critique.md` 设计评审）交叉验证后的合并清单。P0 共 10 条，其中 6 条是 Proposal 内部矛盾。

## P0-1 命名冲突：`Review`（评论）、「复核」动作、`ReviewRecord`（记录）同一个词

**问题**：§4.3 定义 "Review（评论原文与来源）"，同一节又定义 "ReviewRecord（人工修改及跟进记录）"；接口是 `POST /issues/{id}/review`（"保存复核"）；图 1 写 "更新Review（suggested）"；§7.2 AI 输出字段叫 `review_id`。同一个词承担"评论 / 人工复核动作 / 复核记录"三种含义。

**后果**：`suggested` 到底写在 Review 还是 ReviewIssue 无法判定（表 0 里 Review 没有任何状态）；AI 契约的 `review_id` 与 `/issues/{id}/review` 在同一份文档里指两个东西，实现期必然各写一套；日志、权限、统计上不可区分。

**建议**：评论实体改名 **`Comment`**（字段 `platform, shop_id, product_id, source_review_id, review_date, rating, body, content_hash, analysis_status, has_issue`）；关联表 `CommentIssue`；人工动作统一落不可变表 **`IssueAction`**（替代 ReviewRecord）；接口改 `POST /issues/{id}/actions`（body 带 `action`）；AI 契约字段改 `comment_id`。§4 前加 6 行术语表，全文只允许一套词。

## P0-2 Job 粒度与"部分成功"未定义

**问题**：图 1 写"事务落库 + 创建 Job / Review Job Pending"，§4.1 第 3 步写"API 将评论与**对应** Job 事务性落库，返回接收结果和**任务编号**"，接口 `POST /review-batches` 又返回一个任务号。是一批一个 Job，还是一条评论一个 Job？两者后果完全不同：一批一个 Job 时单条失败会拖垮整批、重试重复处理已成功部分；一条一个 Job 时 202 返回哪个 Job、`GET /jobs/{id}` 如何看批次进度。

**建议**：**1 条评论 : 1 个 Job**（AI 调用、重试、幂等的最小单元），`Job` 增加 `comment_id`、`batch_id`，唯一约束"同一 comment 同时最多一个非终态 Job"；`IngestionBatch` 只做接收与校验汇总，`status ∈ {received, validating, rejected, imported, completed, partially_failed}`，`accepted_rows / duplicate_rows / invalid_rows` 在导入阶段写死；分析进度（`analyzed_rows / failed_rows`）由 Job 聚合实时派生，**不在批次表另存计数**（避免双真相）。`POST /review-batches` 返回 `{batch_id, status, job_count}`，**不返回单个 job_id**；批次进度用 `GET /review-batches/{id}`，单条用 `GET /jobs/{id}`。批内一条失败不影响其他 Job，批次按计数显示"部分成功"。若坚持分批 Job，必须写清失败只重跑未成功评论、AI 按 20–50 条/批调用。

## P0-3 Job 重试状态机不闭合（两图不一致 + 无上限 + `claimed` 无租约）

**问题**：图 1 虚线是 `failed` → **`claimed`**，标注"重试 attempts+1"；图 2 虚线是 `failed` → **`pending`**。`docs/architecture.md` 现状是"认领时 attempts+1"且"首版不自动重试"。没有 `max_attempts`、没有退避、没有重试触发入口，没有租约字段；图 2 图注又说"首版不自动恢复"。现有 Worker 认领是"先 select 再 update"（`worker:20-36`），多副本会重复领取；完成/失败写入不校验当前状态，过期 Worker 可覆盖已重领的 Job。

**建议**：
- 重试**只回 `pending`**（禁止 `failed→claimed`）；`attempts` 只在认领时 +1；新增 `max_attempts`（默认 3）、`next_attempt_at`、`lease_expires_at`（认领后 10–15 分钟）、`error_code`。
- 迁移：`pending→claimed→completed | failed`；`failed → pending`（`attempts < max_attempts` 且错误可重试）；`claimed → pending`（租约过期回收，`attempts+1`）；超限 `failed` 终态。
- 触发者只允许两种：`POST /jobs/{id}/retry`（人工）或 Worker 扫描 `failed AND attempts < max_attempts`（自动）；两者都要幂等（并发重试只有一个成功，其余 409）。
- 认领原子化：`SELECT … FOR UPDATE SKIP LOCKED` 或 `UPDATE jobs SET status='claimed', attempts=attempts+1 WHERE id=(SELECT id … LIMIT 1) RETURNING *`；完成/失败写入带 `WHERE status='claimed' AND claimed_at=:seen`（fencing），拒绝过期 Worker 提交。
- 错误分类：`ai_timeout / ai_5xx / db_error` 可重试；`invalid_output` 只在"修复提示后重试一次"时重试，否则直接 failed（结果不伪造）；`comment_not_found` 不可重试。

## P0-4 图 1 把 `confirmed` 之后画成"结束·维持关闭"，`resolved` 与"记录跟进"缺失

**问题**：图 1 的"确认 Issue: proposed → confirmed"分支直接向下指向绿色终点框"**结束：维持关闭 / 新评论只作提示，不进计数**"。但 `confirmed` 在表 0 / 图 2 是"人工已确认"，不是关闭；关闭态是 `resolved（已记录处理完成）`，而图 1 从未出现 `resolved`，也没有 §4.1 第 6 步的"人工记录措施并更新问题组状态"。

**后果**：按图 1 实现会把 `confirmed` 当终态，`resolved` 与跟进记录永远走不到；按正文实现则缺少一段主流程，"人工跟进记录"无法演示。

**建议**：端到端图补 `confirmed → resolved`（记录跟进，写 `IssueAction(action=resolve)`）；删除"确认→结束"的边；绿色终点框移到 `dismissed` 与 `resolved` 之后，文案改为"进入人工跟进 / 已关闭，后续同类评论生成 suggested 关联并提示"。`confirmed` 的出口只能是 resolve / dismiss（误确认）/ merge / split，不能是"结束"。

## P0-5 `dismissed` 不是终态，三处互相矛盾

**问题**：§4.1 第 6 步「由人工决定是否重新打开已关闭的问题组」说明"关闭"可重开；§4.2 表格与图 2 标注 `dismissed` 为"（终态）"；图 1 终点写"新评论只作提示，不进计数"。

**建议**（二选一并统一到正文、表格、两张图）：
- **方案 A（推荐）**：`dismissed` 非绝对终态。收到同类新评论时只累计 `suggested` 关联并产生"待查看提示"，不自动重开；人工可 `reopen`：`dismissed → proposed`（记 `IssueAction`，`reopen_count+1`）。
- **方案 B**：`dismissed` 为终态，新评论只能新建关联旧组的 Issue（`replaces_issue_id`），UI 提示"可能属于已驳回问题组"。
- 无论哪种，都要补规则：`resolved` 重开后历史计数保留，页面同时给"重开前 / 重开后"两个口径。

## P0-6 评论实体没有分析状态，`has_issue` 与证据无处落库

**问题**：§5 要求页面分别显示"接收量 / 成功分析量 / 失败量"，图 1 的 AI 输出是"has_issue 三态 · 类别 · 原文证据"；但实体表里 Review 没有任何状态字段，证据只存在 AI 返回体里，刷新即丢。"成功分析量"只能从 Job 反推，一旦逐条失败隔离就会算错。

**建议**：`Comment` 增加 `analysis_status ∈ {received, queued, analyzing, analyzed, failed}`、`has_issue ∈ {yes, no, unknown}`、`analysis_run_id`、`analysis_error`；证据落 `CommentIssue.evidence_text / evidence_start / evidence_end / evidence_verified`；`unknown` 计入"成功分析但结果未知"（单列，不算失败），`failed` 才计入失败量。

## P0-7 重跑（正文变更 / prompt / 模型升级）会覆盖人工结论

**问题**：§4.3「分析重试采用更新或唯一约束」与 §7.3「评估分析效果」都默认可重复分析；但全文没有 `analysis_run` / `model_version` / `prompt_version`，也没有"重跑不得修改 accepted/rejected"的规则。换模型或改 prompt 后重跑，人工接受/拒绝的关联可能被覆盖成 suggested、被删除或改挂到别的组。

**建议**：引入 `AnalysisRun(id, comment_id, job_id, model_version, prompt_version, category_version, created_at)`；AI 只允许写 `origin=ai, status=suggested` 的行，重跑规则写死：① 旧 run 的 suggested 行置 `superseded_at`（仅限 `origin=ai AND status=suggested`）；② `accepted/rejected` 行永不修改；③ 人工改判只写新 `IssueAction`，`CommentIssue` 保留 `decided_by / decided_at`；④ 正文变更追加 `CommentRevision`，`CommentIssue.comment_version` 记录结论对应的版本。

## P0-8 统计口径不可计算，且图 1 与 §5 冲突

**问题**：§5 写"问题数量 = 去重评论条数"，图 1 终点写"新评论只作提示，**不进计数**"；图 2 注释写"suggested 不计入人工确认数，页面分开显示 AI 建议数与人工确认数"——但从未定义这两个数怎么算、`suggested` 是否计入问题数、`rejected` 是否扣减、`unknown` 是否算有效评论。去重键也不含商品维度，与"同一商品内的分母"不同口径。

**建议**：写死六个口径：
1. 接收量 = `SUM(batch.accepted_rows)`（重复行单列 `duplicate_rows`）；
2. 成功分析量 = `COUNT(comment WHERE analysis_status='analyzed')`（含 `unknown`）；
3. 失败量 = `COUNT(comment WHERE analysis_status='failed')`；
4. 问题提及数 = `COUNT(DISTINCT comment_id) FROM CommentIssue WHERE issue_id=? AND status='accepted'`；
5. AI 建议数 = `CommentIssue WHERE origin='ai'`，其中 `suggested` 单列；
6. 人工确认数 = `status='accepted'`。

关组后新评论仍建 `suggested` 关联，问题数按 accepted 实时算，另设"关组后新增数"，**删除"不进计数"**表述；所有查询接口返回 `as_of` 与 `scope(product_id, date_from, date_to)`。

## P0-9 AI 契约不完整，证据无法校验

**问题**：§7.2 只给示例 `review_id、has_issue、issues[{category, description, evidence}]`，没有：`has_issue` 枚举值、`issues` 为空与 `no` 的关系、`evidence` 定位方式（子串 / 偏移 / 允许改写）、类别是否受控、置信度语义、模型与 prompt 版本、超时与失败分类。不做证据校验，模型会生成原文里没有的"证据"，直接违反 §8"不虚构分析依据"。

**建议**：写死契约：`{comment_id, has_issue: "yes"|"no"|"unknown", issues: [{category_id, description, evidence_text}], model_version, prompt_version}`；四条校验规则：① `has_issue='no' ⇒ issues=[]`，`'yes' ⇒ issues 非空`；② `evidence_text` 必须是对规范化正文（统一全半角/空白）的精确子串，Worker 计算 `evidence_start/end` 并写 `evidence_verified`，定位失败则该 issue 不落库、`has_issue` 降级 `unknown`、Job 记 warning 而非直接 failed；③ `category_id` 来自受控表 `Category(id, name, taxonomy_version)`，阈值与版本记录；④ 一条评论多个问题时每个 issue 独立一行 `CommentIssue`，各自定位证据，`UNIQUE(comment_id, issue_id)` 保证同一问题只计一次。

## P0-10 错误清单"不落库"会丢证据，也无法做批次审计

**问题**：图 1 与 §4.1 第 3 步写"错误清单（行号 + 原因，不落库）"，但 §4.1 第 2 步要求"批量上传、校验和预览"，§8 风险表要求"展示校验结果"。请求返回后错误清单消失，无法下载、对比、复现；行号在用户改完文件后也失去意义。

**建议**：两段式：`POST /review-batches`（multipart + `Idempotency-Key`）→ 201/202 `{batch_id, status:'validating'}`，落 `IngestionBatch`（含 `source_type, file_hash, declared_rows, idempotency_key`）；异步校验结果写 `batch_rows`（`row_number, column, code, message`），`GET /review-batches/{id}` 返回计数与错误摘要，`GET /review-batches/{id}/errors` 分页 + CSV 下载；"修正后重传"生成**新批次**并记 `resubmitted_from_batch_id`，不覆盖旧批次。

# 4. 修订后的目标架构（建议直接写进 architecture.md）

## 4.1 模块与职责

| 模块 | 职责 |
| --- | --- |
| API（FastAPI） | 批次上传 / 校验、评论查询、问题组查询与复核动作、任务状态、健康与指标；所有写操作事务化 |
| Ingestion（API 内） | 编码与列映射、逐行校验、去重 upsert、错误清单落库、批次状态机 |
| Worker | 原子认领 Job（租约）、逐条分析评论（失败隔离）、写 `AnalysisRun` 与关联、失败分类与重试、指标 |
| AI Service | `/extract-issues`（单条或小批量评论）、`/suggest-groups`（同商品归组建议）；规则基线可替换为 LLM；输出 JSON Schema 校验由 Worker 再做一遍 |
| PostgreSQL | 事实表（comments / comment_revisions / ingestion_batches / batch_rows）+ 推断表（issues / comment_issues）+ 审计（issue_actions / analysis_runs）+ 任务（jobs） |
| Adapters | `CsvSourceAdapter`（首版）、未来 `ApiSourceAdapter`；输出统一 `NormalizedComment` |
| Compose / CI | 保持现状，补 worker 指标与失败重放脚本的调用方式 |

## 4.2 数据模型（建议字段）

| 表 | 关键字段 | 约束 / 说明 |
| --- | --- | --- |
| `comments` | id(uuid), platform, shop_id, product_id, source_review_id, rating, review_date, body, content_hash, analysis_status, has_issue, analysis_run_id, analysis_error, created_at, updated_at | `UNIQUE(platform, shop_id, product_id, source_review_id)`；`analysis_status ∈ received/queued/analyzing/analyzed/failed` |
| `comment_revisions` | id, comment_id, body, content_hash, version, created_at | append-only，`UNIQUE(comment_id, version)` |
| `ingestion_batches` | id(uuid), platform, source_type, file_ref, file_hash, declared_rows, accepted_rows, duplicate_rows, invalid_rows, status, idempotency_key, resubmitted_from_batch_id, created_at, finished_at | `UNIQUE(idempotency_key)`；`status ∈ received/validating/rejected/imported/completed/partially_failed` |
| `batch_rows`（错误清单） | batch_id, row_number, column, code, message | 替代"不落库"，可下载 |
| `jobs` | id, job_type(`extract_issues`), comment_id, batch_id, status, attempts, max_attempts, next_attempt_at, lease_expires_at, error_code, error, created_at, claimed_at, completed_at | 唯一约束"同一 comment 最多一个非终态 Job"；认领原子化；租约回收；失败分类 |
| `issues` | id, platform, shop_id, product_id, category_id, title, description, status, created_by(ai/human), merged_into_id, split_from_id, reopen_count, resolved_at, created_at, updated_at | 同一商品 + 类别内归组；`dismissed` 可重开（方案 A） |
| `comment_issues` | id, comment_id, issue_id, status(suggested/accepted/rejected), origin(ai/human), evidence_text, evidence_start, evidence_end, evidence_verified, similarity, analysis_run_id, decided_by, decided_at, created_at | `UNIQUE(comment_id, issue_id)`；人工行不被重跑覆盖 |
| `issue_actions`（原 ReviewRecord） | id, issue_id, comment_issue_id, action(confirm/dismiss/reopen/rename/merge_into/split/followup/resolve/accept/reject/change), from_status, to_status, payload_json, operator, note, created_at | append-only 审计 |
| `analysis_runs` | id, job_id, comment_id, model_version, prompt_version, category_version, input_hash, output_json, status, latency_ms, token_in, token_out, created_at | 评测与复现；重跑保留历史 |

（表名可按组内习惯调整；关键是 **事实 / 推断 / 审计 / 任务** 四类分开，且每条 AI 结论都能追到一次 `analysis_run`。）

## 4.3 修订后的状态机

| 对象 | 状态与迁移 | 说明 |
| --- | --- | --- |
| Job | `pending → claimed → completed`；`claimed → failed`；`failed → pending`（`attempts < max_attempts` 且错误可重试）；`claimed → pending`（租约过期回收）；超限 `failed` 终态 | 认领原子化（SKIP LOCKED / RETURNING）；`attempts` 认领时 +1；禁止 `failed→claimed`；完成 / 失败写入带 fencing 条件 |
| 评论分析 | `received → queued → analyzing → analyzed(yes/no/unknown)` 或 `failed`；`failed → pending`（人工重放）；正文变化 → 新 `analysis_version` | 统计口径按评论聚合 |
| Issue | `proposed → confirmed`；`proposed → dismissed`；`confirmed → resolved`；`resolved → confirmed`（重开）；`dismissed → proposed`（人工重开，方案 A）；`confirmed → dismissed`（误确认） | 改名 / 合并 / 拆分不改状态，只写 `IssueAction`；合并后原组从活跃列表排除 |
| 评论关联 | `suggested → accepted / rejected`；`accepted ↔ rejected`（改判，留审计）；重跑只 supersede `origin=ai AND status=suggested` 的行 | `accepted` 是唯一计入"问题提及数"的状态 |

## 4.4 接口清单（建议，12 组）

| 接口 | 作用 | 要点 |
| --- | --- | --- |
| `POST /review-batches` | 上传 CSV / JSON 批次 | multipart + `Idempotency-Key`；返回 `{batch_id, status, job_count}`，不返回单 job_id |
| `GET /review-batches/{id}` | 批次进度与计数 | `accepted / duplicate / invalid / analyzed / failed` |
| `GET /review-batches/{id}/errors` | 错误清单 | 分页 + CSV 下载 |
| `GET /comments` | 评论列表 | 商品 / 日期 / `analysis_status` / `has_issue` + cursor |
| `GET /comments/{id}` | 评论详情 | 原文、版本、AI 输出、关联问题、证据 |
| `GET /issues` | 问题组列表 | 商品 / 状态 / 类别 / 日期 / `sort=accepted_count` + cursor |
| `GET /issues/{id}` | 问题组详情 | 关联评论 + 证据 + 计数口径 + actions 历史 |
| `POST /issues/{id}/actions` | 复核动作 | `action + expected_version`；confirm / dismiss / reopen / rename / merge / split / followup / resolve |
| `POST /comment-issues/{id}/decision` | 关联决策 | accept / reject / change |
| `GET /jobs/{id}` | 单任务状态 | `status, attempts, max_attempts, next_attempt_at, error_code, error` |
| `POST /jobs/{id}/retry`、`POST /jobs/{id}/recover` | 人工重试 / 卡死回收 | 幂等，冲突 409 |
| `/health/live`、`/health/ready`、`/metrics` | 运维 | 沿用现状，补 worker 指标 |

## 4.5 关键流程（批次 → 问题组）

1. 上传 CSV → 落 `ingestion_batches(validating)`，返回 202；异步校验：编码 / 列 / 行数 / 必填 → 写 `batch_rows`。
2. 校验通过：逐行规范化（dry-run 去重）→ 写 `comments(analysis_status=received)`；批次置 `imported`，同一事务内为每条评论建 `jobs(pending)`。
3. Worker 原子认领（租约）→ 调 AI（单条或 20–50 条小批）→ 校验 JSON 与证据 → 写 `analysis_runs` + `comment_issues(suggested)` + `issues(proposed)` → 评论置 `analyzed`，Job `completed`。
4. 归组后处理（可重跑）：按 `(product_id, category_id)` 召回已有组，命中 upsert 关联，未命中建新组；并发用唯一约束 + advisory lock 兜底。
5. 人工复核：查看 Issue 与原文证据 → confirm / dismiss / 改名 / 合并 / 拆分 → 写 `issue_actions`；确认后记录跟进 → `resolved`；可重开。
6. 统计：按 `comments.analysis_status` 出接收 / 成功 / 失败；按 `comment_issues` 去重计数出问题提及量；页面拆开 AI 建议数与人工确认数，并显示分析覆盖率与 `as_of`。

# 5. 四人分工

## 5.1 协作模式：契约先行 + 四线并行

**结论：以并行开发为主，但不是"全并行"；流水线只保留在三个关口。** 判断标准只有一句话——**跨人共享的东西串行，各人模块内部的东西并行**。

**为什么不能纯流水线**：4 个人、契约与接口是硬前置。流水线会让 R3、R4 在等待契约时空转，R1 变成单点阻塞；R1 一旦延迟（迁移、契约都是他的），全队停摆，最后只能临时补。

**为什么不能纯并行**：四个人共享一个数据库和一套契约（`services/common/schemas.py`、`alembic` 迁移、OpenAPI）。契约没定就并行，等于各写一版；多人同时改 `models.py` 会互相覆盖，联调时全部返工。

**真实依赖是 DAG，不是链条**。看起来"取数→分析→归组→复核"是串行链条，但代码层只要把契约和假数据先立起来，四条线就可以同时开工：

| 真实依赖 | 解除方式 |
| --- | --- |
| 数据模型 / 契约 → 所有人 | 冻结 `schemas.py` + `0002` 迁移 + OpenAPI，配 mock |
| R3 AI 输出 → R2 Worker 校验 | JSON Schema 先定，R2 用 fake AI 返回固定 JSON |
| R2 Worker → R4 复核页的数据 | R4 用 seed 数据 + 契约字段开发 |
| R1 批次入口 → 端到端联调 | mock 批次 + seed，在联调阶段合并 |

**三个串行关口**：

1. **契约冻结**：R1 主笔，全员评审，冻结 `schemas.py` + OpenAPI + `0002` 迁移 + mock AI + seed；此后任何人改契约都要 PR + 全员确认。
2. **迁移执行**：只有 R1 在合并/发布时执行 `alembic upgrade`；其他人提字段需求 issue，不自己写迁移、不自己改 DB。
3. **联调 / 回归**：在关键节点各跑一次，按"上传 → 分析 → 归组 → 复核"顺序串起来跑，其余工作不互相等。

**并行解耦的三个工具**：

- **Mock AI 服务**：`AI_SERVICE_URL` 指向返回固定 JSON 的 fake（或 `docker compose --profile mock-ai`），R2、R4 不依赖 R3 的模型是否可用。
- **Seed + fixtures**：`scripts/seed_demo_data.py` 固定一批箱包评论，R4 的页面/接口先跑起来。
- **OpenAPI 契约**：Worker、AI、前端都按同一份 schema 校验，接口变更同步更新，禁止口头契约。

**契约冻结前的并行准备**：

| 人 | 可先做 |
| --- | --- |
| R1 | `0002` 迁移草案 + 字段清单；冻结 schemas / OpenAPI、CSV 样本、批次 API 骨架 |
| R2 | Job 表改造草案；原子认领 / 租约 / 重试字段与实现、接入 fake AI |
| R3 | 标注样本 + 规则基线；提取 JSON Schema、证据校验函数、mock 输出 |
| R4 | 页面线框 + 接口清单；seed 数据、issues / actions API 骨架、Swagger 走查 |

**反模式（明确不要做）**：

- 不做"一人做完再交给下一人"的瀑布：拖到最后会来不及，且后手没有上下文。
- 不在契约冻结前写业务实现：写完还要按新 schema 改一遍。
- 不同时改 `models.py` / 迁移 / `schemas.py`：这是唯一强制串行的区域。
- 不把大 PR 拖到收尾阶段合并：冲突会集中爆发。

## 5.2 分工原则

1. **契约先行**：开工前冻结 OpenAPI + `services/common/schemas.py`；之后任何人改契约都要 PR 评审，避免四人各改各的（执行方式见 §5.1）。
2. **单一写权限**：数据模型与迁移只有一个人（R1）能改；其他人通过 PR 提字段需求。
3. **每人对自己模块的测试负责**：不接受"测试是 R4 的事"；R4 负责端到端与 CI，不负责替别人补单测。
4. **模块 owner 而非文件 owner**：跨模块改动由 owner 主写、另一人评审；定期同步 + 集成检查。

## 5.4 协作执行细则

- **分支与 PR**：`main` 保护；每人一条 feature 分支；PR 模板已存在，必须写"改了哪个契约 / 迁移 / 测试"；PR 控制在合理范围，评审通过、CI 绿才合并。
- **契约变更**：任何人改 `services/common/schemas.py` 或 OpenAPI，都要开 PR 并 @ R2、R4 确认；同步更新 mock 与测试 fixture，不允许"先改代码后补契约"。
- **迁移规则**：迁移只有 R1 写、只有 R1 在合并/发布时执行；其他人需要字段先提 issue（字段名 / 类型 / 是否可空 / 索引 / 用途）。
- **接口协作**：R3 的 AI 输出变化必须同步 R2（Worker 校验）与 R1（schema）；R1 的迁移变更提前通知全员。
- **交付检查**：闭环必须能演示"CSV → 问题组 → 复核"，质量项可以后续补齐；不做与单平台入口无关的范围扩张。
